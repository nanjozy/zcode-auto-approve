# ADR-0005：未命中与失败一律 pass-through，v1 不主动 deny

- 状态：Accepted（默认采用推荐方案，待用户复核）
- 日期：2026-09-15

## 背景

`PermissionRequest` hook 的输出可以表达三种行为：approve（放行）、空（直通回人工审批）、deny（拦截，stdout `{"decision":"block"}` 或 exit 2）。此外还存在事件时机选择：也可改用 `PreToolUse` 提前决策。

## 决策

1. 脚本只有两种输出：`{"decision":"approve"}`（exit 0）或**空 stdout**（exit 0）。**永不输出 deny、永不 exit 2。**
2. 一切未命中、不确定、解析失败、规则文件损坏的路径都收敛到空输出直通（失败语义总表见 design.md §7.2）。
3. 监听 `PermissionRequest` 而非 `PreToolUse`：deny 语义对两者分别表现为拒绝审批与阻断执行，本项目不做拦截，选更贴近审批场景的 `PermissionRequest`。

## 理由

项目的收益函数是"减少弹窗，最坏情况不多弹一次窗"。deny 是一个**阻断用户工作流**的行为——一旦规则误判，用户会被自己写的 hook 拦住，且模型无法绕过；而"该放行没放行"的代价只是多一次点击。把误伤面从"阻断"压到"多一次点击"是本 ADR 的核心。

同理，v1 不使用 `permissionUpdates`（把放行规则持久化进 ZCode 权限系统）：一次 hook 放行应是**单次**决定，持久的规则会让"改了 rules.json 想收紧"变得不可逆地困难，留待 M4 单独设计。

## 后果

- 正面：hook 的错误面与攻击面都单向安全——再离谱的 bug 也只会退回人工审批；denylist 语义简化为"永不自动放行"而非"拦截"。
- 负面：真正的危险命令仍会弹窗打扰（用户手动拒绝即可）；若未来想要"危险命令直接拦下不弹窗"，需在 M4 引入显式开关并重新评估误伤。
