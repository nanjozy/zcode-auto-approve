# ADR-0004：规则外置 JSON + JSONL 审计日志

- 状态：Accepted（默认采用推荐方案，待用户复核）
- 日期：2026-09-15

## 背景

规则可以硬编码在脚本里，也可以外置；自动放行行为是否留痕是可选项。

## 决策

1. **规则外置**：`rules.json` 与脚本同仓库（schema 见 design.md §5.2），支持环境变量 `ZCODE_AUTO_APPROVE_RULES` 覆盖路径。调规则不改代码，规则变更走 git 可追溯。
2. **JSONL 审计日志**：每次 hook 调用（放行**与**直通）向 `~/.zcode/zcode-auto-approve/audit/audit-YYYY-MM-DD.jsonl` 追加一行，记录时间、工具、命令原文、命中规则或直通原因码（`reasonCode`）、`riskLevel`、`cwd`、`sessionId`。日志放在仓库外的用户目录，避免误提交。

直通也记日志是刻意选择：出问题时第一反应往往是"为什么这条**没有**自动过"，原因码（deny-pattern / unanalyzable / no-match / error…）直接回答它。

## 备选方案

- **规则硬编码**：少一个文件，但每条规则调整都要改代码 + 回归测试，摩擦大。
- **规则外置但不记日志**：干净，但自动放行变成黑盒，无法回溯"刚才为什么放行了这条"，与安全工具的基本要求相悖。
- **结构化日志（SQLite 等）**：查询能力强，但引入依赖与锁问题；JSONL + `grep`/`jq` 对单用户日量级绰绰有余。

## 后果

- 正面：规则即配置、放行即留痕；日志按天分文件，`.gitignore` 已排除。
- 负面：每次 hook 调用多一次小文件写（追加一行，量级可忽略）；日志含命令原文，若命令里带密钥则日志同敏感——已在 design.md §7 威胁模型表 T7 披露"勿把密钥写进命令行"。
